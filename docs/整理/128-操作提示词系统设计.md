## 1. 目标与原则

**目标**：让玩家在操作面板（interaction-panel）上读懂——当前要做什么、操作的实际效果（伤害/距离/费用/目标数）、以及**不操作的后果**。提示词中的数值与部分词条（如攻击次数、耐久、炸弹数、CD、必暴额度、剩余次数）必须**随实际对局状态改变**，不能是写死的文案。

**原则**（延续 v1）：
- 提示词数据一律来自**服务端投影**（`OfferPreview` 结构化字段 / 窗口 `context.promptData` / `CardView.summary`），客户端只做文案渲染，**不自行计算规则**。
- 已确认采用「**服务端投影结构化字段**」：服务端填数值，客户端按模板渲染。

**现状确认（v2 调查结论）**：
- 服务端 `projection.ts:48` 已为每张卡投影 `CardView.summary`（现恒为空串）、`coreStats`、`badges`——管道存在、数据未填。
- 协议 `OfferPreview` 已含 `range/damageStructure/costSummary/distanceByTarget/slot/weaponRef/modeId`，除 `range`（攻击已填）外**全部未填充**。
- 窗口报价 `windowOffer`（projection.ts:81）preview 恒为 `{costSummary:null}`；`attackResponse` 窗口 context 无任何攻击详情。
- 客户端 `promptHints[kind]`（GameView.vue:87）是静态文案表，`cardDescriptions/characterDescriptions`（localization/）是静态数值文案——均不随状态变化。

| 层级 | 位置 | 内容 | 数据源 |

| L1 面板提示 | interaction-panel 顶部 `.prompt-hint` | 操作意图 + 关键效果 + 不操作的后果 | 窗口 context → `promptData` → 客户端模板渲染 |

**投影契约**（本次设计核心）：
1. `OfferPreview` 字段由服务端按报价类型填充：`damageStructure`（攻击）、`costSummary`（费用）、`distanceByTarget`（攻击目标距离）、`range`（已有）。
2. 窗口 `context` 增加 `promptData?: {…}` 结构化字段（攻击快照、数值摘要、放弃后果），独立于既有 `legalCardRefs/legalTargetRefs` 等引用字段。
3. `CardView.summary` 由服务端按卡牌 DSL 生成（客户端 `cardSummary` 已支持服务端优先）。

## 4. 操作全集与内容规格

> 编号沿用 v1 的 A/B/C/D/E/S/P/B/SYS 体系，扩展补齐。每类给出提示词**必含内容**与**动态数据源**。所有数值均需随状态变化，非写死。

### 4.0 句子构成规范（六角色）

所有操作提示词由六角色构成。提示词是**面向玩家的操作摘要**：比卡牌/角色详情简短，只保留操作必需信息（去掉规则解释、生效时机、限制条件），目的是让玩家扫一眼就能操作。

| 角色 | 何时出现 | 内容规则 | 数据源 |
|---|---|---|---|
| **主语**（谁行动） | 总是 | 自己的操作写"你"；他人发起写其**角色名**（如"精灵"）；武器/技能为主体写"武器【名】/技能【名】" | S4 角色名 |
| **宾语**（对谁/对什么） | 有目标时 | 目标**角色名**（如"精灵"）；目标卡牌/槽位；全场攻击写"所有在场角色" | S5/S7 |
| **手段**（用什么） | 涉及武器/技能/卡牌时 | "使用武器【火焰之鹰】(方式1)"/"发动技能【狂战】"/"打出【药水】" | S6+S1 |
| **报价**（支付什么） | **只在有使用选择/资源决策时** | 杀×N、次数×M、弃牌×N、血量-N；固定必付的并入效果栏；不可支付时高亮原因 | S2 `payable`+`costs` |
| **效果**（结果数值） | 总是 | 数值化：伤害段×元素、回复量、摸牌数、目标数、附加效果(破防/必暴/免疫/冰冻/感电) | S1/S6 |
| **后果**（不操作会怎样） | 响应/濒死/判定/触发/可放弃类 | "不响应→承受N点伤害→濒死"、"放弃→随机判定"、"超时→pass/随机" | S3/S5 |

**句子模板**（L1 面板提示，一段或两行）：
```
[主语][手段]对[宾语][动作]：[效果]；[报价]；不[动作]→[后果]
```
L2 报价按钮 = 动作名+效果摘要（≤12 字）。L1 每行约 40 字内，超出拆为「意图 + 效果 / 后果」两行。

**简洁性原则**：数值全部来自投影；文字模板静态；与详情抽屉（完整规则）形成「摘要/详情」两层，互不替代。主语省略规则：本窗口行动者即玩家本人时默认"你"，不重复角色名。

### 4.0.1 配色语义（token 着色）

提示词文本以中性色为底，**仅对细粒度 token 着色**（角色名、武器/卡牌名、数值、效果名），不整句变色。三套色系按 token 类型区分、互不冲突。效果只显示**直接效果**（如"冰冻""伤害2"），不展开多段/后续结算。

**① 关系色——角色名（主语/宾语）**，按当前查看玩家的视角：
| 角色 | 颜色 | 取值 |
|---|---|---|
| 自己"你" | 绿 | `#6fdda0` |
| 队友 | 蓝 | `#7fc4e8` |
| 敌方 | 红 | `#ff9aa8` |

**② 卡牌印刷色——武器/卡牌名**（复用现有 `game-card__name--*`，`client/src/styles/base.css`）：
| 印刷色 | 取值 |
|---|---|
| 白 | `#eef4f7` |
| 绿 | `#7fe0ae` |
| 蓝 | `#7fc4e8` |
| 橙 | `#ffb37a` |
| 红 | `#ff9aa8` |

**③ 语义色——数值与效果名**（按规则分类：`damageType` normal/shield/hp + `element` fire/poison/electric + 状态 frozen/electrified，见 `rulesets/v1.3.4/weapon-rules.json`）：
| 语义 | 颜色 | 取值 |
|---|---|---|
| 普通伤害数值 | 蓝 | `#7fc4e8` |
| 护盾伤害数值 | 钢灰 | `#9fb3bd` |

| 火（元素） | 橙 | `#ffb37a` |
| 毒（元素） | 深绿 | `#3da86b` |
| 感电（元素）/电击（状态） | 黄 | `#ffd27b` |

### 4.2 攻击响应（窗口 `attackResponse`，报价 `respond`）

| 响应方式 | 必含内容 | 动态数据源 |
|---|---|---|
| B1 出【闪】 | 抵消整次攻击全部段；攻击来源×伤害、距离、攻击类型 | **S3 攻击快照入 context**（新增） |
| B2 近战格挡 | 抵消近战攻击；激光/场地不可格挡实时判定 | S3+`responsePolicy` |
| B3 防具判定/挡牌 | 判定颜色条件、防具效果 | S3+S6 防具 DSL |
| B4 技能响应（翻滚/刺客信条/网瘾/羊叫兽/大宝贝儿/神圣屏障/乾坤挪移） | 技能效果+代价、未响应的后果(感电×x/掉血) | S3+S6+S4 标记 |
| B5 放弃 | **不响应的后果**：承受上述伤害→濒死判定 | S3 伤害总览 |

**样例**：`【响应】精灵用【火焰之鹰】攻击你：远程2 · 伤害2；可出【闪】抵消全部段；不响应将承受2点伤害`。主语=攻击者角色名（如"精灵"）、手段=武器名、效果=攻击类型+伤害、后果=未响应承受伤害。响应按钮各自标注效果差异（出闪→抵消全部段 / 格挡→抵消近战）。

### 4.6 角色技能窗口（39 特殊窗口，逐条见 §5 表）

统一规格：**技能名+效果数值、当前状态(CD/次数/炸弹/能量/耐久)、目标范围、放弃后果**。每窗口的数值随对局状态变，例如：
- `weaponW61Choice`（扳手）：伤害 1×n，n=公开扳手耐久；拆除或伤害二选一的后果。
- `trapBombDetonation`（引爆）：炸弹数 x，每弹 1 点场地伤害段。
- `demolitionWeaponOverflow`（拆迁超限）：三档 requiredCount（常规/第三武器）。
- `darkKnightFinalStrike`（大骑士最后一击）：剩余黑剑数逐剑攻击。
- `elementSatchelFlameDismantle`（烈焰锦囊）：可拆张数范围、隐藏牌计数。
- `foresightDrawChoice`（未卜先知）：展示 N+2 选 N，剩余牌弃置。
- `criticalPenetration`（暴击穿透）：modeId+payable，再出杀追击另一目标。
- `c6FocusedBombardmentRequest`（C6 定点）：requestIndex/successes，未打出则受 5/2 场地伤害。

**样例**：`【扳手】武器【扳手】命中：伤害1×耐久(当前3)，或改拆目标1张牌并耗1耐久`。每个技能窗口都必须由 4.0 六角色构成，主语=技能持有者角色名（他人窗口写角色名，本人写"你"），效果数值随 markers/runtime 变。

### 4.9 选择器 L3（`selectionSpecs`）

| 操作 | 必含内容 | 动态数据源 |
|---|---|---|
| S1 选目标 | 目的(攻击/增益/拆除/转移)+数量 | `context.purpose`+spec |
| S2 选卡牌 | 目的与后果(拆除→弃置/交付→给谁/弃置→进弃牌堆) | `context.purpose`+spec |

## 6. 服务端投影缺口清单（实施清单，按依赖序）

1. **攻击报价补摘要**（`app/projection.ts` `playOffer`）：对 `kind:"declareAttack"`（及 `blackSwordAttack`）填 `preview.damageStructure`（逐段字符串/结构化数组，源自 `mode.damageSegments`）、`costSummary`（杀×N·次数×M，源自 `mode.costs`）、`distanceByTarget`（各合法目标距离，源自 S7）。协议字段均已存在，无需改 schema。
2. **攻击响应窗口附攻击快照**（`engine/response.ts` 开窗处）：context 增 `attack:{attackerSeat,targetSeat,weaponLabel,modeRange,attackTypes,damageSegments}`（脱敏：只含公开信息；伤害来源/武器名/距离/类型）。
3. **濒死窗口附现状**（`engine/dying.ts`）：context 增 `dyingHp,damageSourceLabel`。
4. **窗口 context 补 `purpose`**：选择器类窗口（statueCardSelection/qiBallDismantle/triggerCardSelection/minerSourceDismantle 等）加 `context.purpose`（dismantle/deliver/show/transfer/respond…），供客户端 L3 生成"为<目的>选择 N 张牌"。
5. **卡牌 summary**（`app/projection.ts:48`）：`summary:""` 改为按卡牌 DSL 生成（药水回复量/武器伤害/特殊牌效果，含随状态变化的数值如扳手耐久）。客户端 `cardSummary` 已支持服务端优先。
6. **特殊窗口数值补全**（§5 标注 📎/➡ 者）：按窗口逐个在 context 补 `promptData` 数值字段（黑剑数/耐久/剩余次数/伤害段/效果名等）。

## 7. 客户端实施清单

1. `GameView.vue`：`promptHints` 静态表升级为 `promptRenderers[kind](snapshot)` 模板函数表，L1 按 4.0 六角色构成渲染 `context.promptData` 数值；无数据时回退现有静态文案。模板收尾词固定（"…；不…→…"），数值占位符来自投影字段。
2. `offerLabel`：结合 `offer.preview`（damageStructure/costSummary/range）生成 L2 摘要（动作名+伤害+费用）。
3. 攻击响应 L1：用 context 攻击快照生成"来源×伤害，距离X，不响应将承受…"。
4. 选择器 L3：按 `context.purpose`+spec 生成"为<目的>选择 N 张牌"。
5. `CardDetailDrawer`/`GameCard`：summary 优先用服务端投影（已有 `cardSummary` 机制）。
6. 状态词条：`PlayerView.statuses`(string[]) 映射静态文案（冰冻/感电/遁地/无敌…），数值（感电标记、剩余额度）来自 `markers`/`electricMark`。
7. **token 着色**：模板渲染为带 class 的富文本片段，颜色按 4.0.1 三套色系；角色名关系色由客户端据 viewer 座位与 `publicView.players[].team` 计算（同队=队友、异队=敌方）；`promptData` 需投影 `actorRef/targetRefs` 供客户端定位着色对象。

## 8. 测试与验收口径

- 每类操作至少有一个 L1 模板；攻击/响应/濒死/判定/技能五类必须展示**随状态变化的动态数值**（伤害/距离/血量/颜色/次数）。
- 提示词数值与真实对局一致：在 SKB_TEST_MODE 环境构造状态，断言 L1 文案含期望数值（如扳手耐久 n、攻击次数余量、炸弹数）。
- 客户端不做规则计算：所有数值来自投影字段。
- 协议 schema 校验通过（`validateProtocol`）、两端构建与全量测试通过；新增 `darkKnightStasis` 式协议扫描测试确保新投影字段合法。
