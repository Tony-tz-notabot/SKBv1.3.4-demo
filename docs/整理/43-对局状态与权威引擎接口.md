# 对局状态与权威引擎接口

## 一、分层

对局实现固定分成三层，禁止互相代替：

1. `AuthoritativeGameState`：服务器内部完整状态，包含隐藏牌、区域顺序、运行时标记、窗口、栈、持续期、随机记录和全部角色状态；
2. `DomainEvent`：一次合法提交产生的有序领域事件，用于审计、表现和恢复；
3. `GameSnapshot`：按具体观看者过滤后的客户端投影，只包含该观看者有权知道的数据和当前合法操作报价。

Vue只能读取第三层。客户端选择不会直接修改状态，只会提交现有 `offerId` 和严格选择结果。

## 二、最小权威状态

`protocol/v1.3.4/engine-contract.schema.json`登记了第一版最小状态。2026-08-01已先同步开局生命周期边界：

- 游戏、规则版本、修订号、事件序号和`setupRedraw | inProgress | ended`生命周期；
- `setupRedraw`期间保存首座、统一截止时间及四座`decided/used`；此时轮次可为0，行动座位和阶段为空，不能伪装成准备阶段；
- 正式对局中的轮次、行动座位和当前阶段；
- 四名角色的在场/生命状态、血盾、铁盾、状态、标记和额度；
- 全部卡牌实例及所在区域的有序引用；
- 当前提示/响应窗口、结算栈；
- 持续实例和延时效果；
- 可复现的随机结果记录；
- 胜负状态。

死亡未淘汰、离场和淘汰分别建模，不能只用单一布尔值。卡牌模板来自冻结规则包，状态中只保存实例引用及运行时差异。

## 三、引擎操作

引擎边界只提供五种操作：

- `createGame`：按规则版本和四个座位创建初始状态；
- `handleCommand`：验证修订、提示窗口、报价、目标和费用后原子提交；
- `handleTimeout`：按窗口的超时策略执行放弃、默认值或随机合法操作；
- `projectViews`：从同一权威提交产生个人、队伍、公开或观战投影；
- `restoreSnapshot`：恢复持久化快照并继续事件序列。

接受结果必须同时返回新修订、领域事件和受众投影。拒绝结果不得改变状态，返回稳定 `reasonCode/messageKey`。随机选择必须写入 `RandomRecord`，回放时不重新随机。

## 四、原子提交顺序

一次命令的固定顺序为：接收 → Schema验证 → 幂等检查 → 修订检查 → 当前窗口/报价检查 → 目标与费用重验 → 执行DSL → 处理触发/响应/濒死直至稳定边界 → 胜负检查 → 提交新修订及事件 → 按受众过滤投影 → 持久化。

任何中途异常都必须回滚整个提交，不能留下已扣费用但效果未完成的半状态。

## 五、当前客户端消费验证

已用现有 `GameSnapshot` 实际实现第一版Vue四方桌面，包括阶段、四座旋转、角色图、血盾、铁盾、状态、手牌数、装备、牌库、弃牌、私有手牌及服务器报价面板。实际渲染证明现有协议可支撑首版骨架；判定区、装备槽位语义和详情投影将在真实消费端出现明确缺口时再扩展。

校验入口：`node tools/validate-engine-contract.mjs`。

统一完整权威状态模型已于后续阶段实现，详见`55-统一完整权威状态模型实现说明.md`。本文件中的最小契约现已扩展为实际服务器模型，并由运行时跨字段不变量验证保护。
