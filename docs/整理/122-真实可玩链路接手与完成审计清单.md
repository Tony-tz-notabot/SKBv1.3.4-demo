## 二、Goal 完成的必要证据

以下项目必须全部具有当前工作树中的直接证据，才能宣布 Goal 完成：

1. 服务端应用层
   - 四人房间完整生命周期、房主权限、座位与队伍固定映射。
   - 受认证身份、断线宽限、重连恢复和服务重启恢复。
   - 所有命令幂等，包括进程重启后的重复命令。
   - 所有可达手动窗口都有明确超时行为。
2. 全量命令路由
   - 每个服务器报价均存在唯一执行适配。
   - 每个适配均验证权限、修订、prompt、offer、费用、目标和当前合法性。
   - 拒绝不污染权威状态。
3. 全量受众投影
   - 玩家本人、队友、对手、观战者的公开/私密字段分别验证。
   - 手牌、隐藏展示、随机手牌选择、选角候选不泄漏。
   - 所有 `InteractionOffer` 有精确的选择类型、上下限和合法引用。
4. 协议与事件
   - 每条入站命令、快照、命令结果和演示事件均通过 v1.3.4 schema。
   - 每种领域事件映射为准确的演示事件，不能只以通用占位掩盖关键信息。
   - 断线重连以后按 revision/eventSeq 去重且不会重复播放旧动画。
5. Vue 全部游戏操作
   - 服务器报价中的手牌、装备、判定区、目标、颜色、模式、数值、确认均可操作。
   - 不进入详情仍显示卡牌/角色基础信息；详情可打开；合法操作高亮。
   - 本人视角座位旋转正确；武器常亮预选和空槽/手刀边界正确。
   - 全体/队伍聊天、图片映射和默认占位图可用。
6. 部署链路
   - 一个明确命令可启动服务器并提供 Vue SPA、静态素材、健康检查和 WebSocket。
7. 端到端
   - 四个真实连接从建房、准备、选角、重摸进入游戏。
   - 至少覆盖普通攻击、响应、多段/多目标、濒死救援、阶段超时、断线恢复。
   - 对局实际到达合法胜负状态。
   - 过程中每条客户端消息通过协议校验，且没有隐藏信息泄漏。

武器总验收和跨规则组合冲突审计依作者决定后置，不作为进入本 Goal 的前置工作；但本 Goal 使用到的普通攻击链路仍必须可玩。

## 四、注册表验收方法

### 4.1 出牌阶段

权威清单位于 `server/src/app/playRegistry.ts` 的 `entries`。

每个 entry 至少增加一个表驱动测试，依次证明：

1. 构造一个真实可达的 `playPhaseAction` 状态；
2. `playOffers` 返回报价；
3. `GameProjector.game` 将报价投影为合法协议；
4. 选择项引用与原始报价相符且隐私正确；
5. 将客户端选择送入 `executePlayOffer`；
6. 对应 Session 接受并产生预期事件/状态；
7. 同 commandId 重放得到相同结果；
8. stale revision、非法卡牌/目标被拒绝且状态不变。

重点检查：普通攻击分别使用 `killCards`、`resourceCards` 和 `targets`；合成材料可能同时来自手牌与装备；主动丢弃/拆除需要选择公开装备引用。

### 4.2 专属窗口

权威清单位于 `server/src/app/windowRegistry.ts` 的 `factories`，核心窗口直接位于 `gameService.ts`。

必须从 `PendingWindowState.kind` 的所有真实生产点反向建立矩阵，而不是只检查注册表已有键。每类标记为：

- `automatic`：引擎无需玩家命令自动处理；
- `core`：`gameService.ts` 直接处理；
- `registry`：`windowRegistry.ts` 处理；
- `missing`：尚无应用层处理，必须补齐。

特别复核这些可能遗漏或由其他会话间接处理的名称：

- `assassinCreedDodge`
- `blackSwordAttack`
- `crystalCrabPassivePincer`
- `demonmancerHellfireJudgment`
- `ghostCrownRangedInvalidation`
- `meleeCounter`
- `rangerRoll`
- `taoistReflection`

不能仅凭字符串搜索认定它们都是独立窗口；应查看真实 `pendingWindows.push`/窗口创建函数及对应行为测试。

### 4.3 超时

对每个可达窗口使 `deadlineAt <= now`，调用 `GameService.timeout`，验证：

- 有利可选操作默认不发动；
- 锁定/不利操作按正式裁定随机；
- 随机使用权威随机源并写随机历史；
- 超时后自动调度继续到下一稳定边界；
- 不会在 250ms tick 中反复处理同一过期窗口。

## 六、已知实现风险

- `playRegistry.ts` 的 `standard` 会用 `(state, ruleset, deadline)` 构造会话；JavaScript 会忽略多余参数，但若某 Session 第二参数并非 ruleset，必须使用专门 factory。
- `executePlayOffer` 使用一个包含常见字段的命令对象适配不同 Session；字段名并非天然保证一致，必须用真实测试证明。
- `windowRegistry.ts` 同样采用通用命令对象，目前未逐类验证 `choice/mode/amount/cardRef/targetRef` 的正确键名。
- `projection.ts` 对原始报价与窗口 context 进行通用推断；任何隐藏牌窗口和多选择窗口都必须专门审计。
- 当前成功命令主要通过全量快照通知客户端，演示事件广播仍不完整。
- 当前 userId 查询参数只能提供恢复便利，不能提供身份真实性。
